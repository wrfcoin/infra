# Workstation standby and USB outage check

Refs infra#970 and infra#966. After a machine restart, detached USB tokens can leave the workstation node and oracle attester stopped with exit128/255. The existing boot overlay is present, but its container-health watcher lists running containers and watches healthcheck streaks. This additional host check covers stopped containers and absent pinned USB devices even when the stack's alert receiver is unavailable.

An owner-installed host job invokes `python3 scripts/check-standby-usb.py` with `--node-usb-device` and `--attester-usb-device` set to the deployment's pinned `/dev/bus/usb/BBB/DDD` source nodes. A synthetic invocation is `python3 scripts/check-standby-usb.py --node-usb-device /dev/bus/usb/001/002 --attester-usb-device /dev/bus/usb/001/003`; these numbers are test examples, not hardware inventory. The owner records the actual expected paths in the host job configuration. Both documented desktop overlays map the whole USB bus: explicit expected pins let this check verify the tokens under those mappings without changing the overlays. Each flag can repeat for multiple pins. Containers with exact source-device mappings can also derive their pins from Docker without arguments.

The check inspects exactly `wrfcoin-testnet-node` and `wrfcoin-testnet-oracle-attester` through the local Unix Docker socket, selecting name, running/status, exit code and device mappings only. Each inspect has a five-second timeout; there are two sequential inspections. It checks every exact source pin and expected pin using character-device stat; an expected pin must be covered by the container's exact or whole-bus mapping. It reads no environment files, container environment, healthcheck output or daemon error text.

The host job needs Python3, the Docker CLI and permission to inspect the local Docker socket and USB metadata. USB paths come from each existing container's device configuration; absent container configuration cannot establish a pin and produces an inspection alert. No secrets or expected key identities are needed.

Exit0 and an INFO/PASS JSON line require both containers running and every USB source/expected pin present as a character device. Exit1 and CRITICAL JSON on stderr report each stopped container and unavailable device, including both conditions together. Missing containers, inaccessible Docker, malformed state, missing pin configuration or whole-bus mappings without expected pins produce nonzero results. A broad `/dev/bus/usb` mapping alone cannot prove that a particular token is attached. This checker targets the workstation with concrete device pins; the N5/CT101 host-pcscd/socket deployments need a separate policy. It does not authenticate the token, prove the intended key is inserted, sign, restart containers, alter mappings or invoke usbipd.

## Alert sink and scheduling design (owner decision)

Run as a host/WSL job after the Docker engine starts and then every60 seconds, independently of node, attester, compose boot-heal and the container watcher. Retain stdout/stderr and exit status in the host job journal. A nonzero invocation should emit a critical `StandbyUsbUnavailable` notification through an owner-selected off-workstation receiver. Group on workstation and container; deduplicate repeated failures, retain the first failure time, and send recovery only after a later successful check. Treat inspect/pin uncertainty as an alert, never success. Polling may observe a transient stopped state during owner maintenance; the job's maintenance policy belongs with the selected sink.

The existing same-host alert-receiver is unsuitable as the only sink for this outage class. Owner choice: A install an independent host job with an external receiver and missed-heartbeat alarm (recommended), B retain local logs/exit codes until a receiver is chosen. An independent observer must detect the workstation/WSL itself being down; this local process cannot run in that state. No notification transport, credentials, scheduler installation, compose/image change or live invocation is included here.

## Verification

`pytest -q scripts/tests/test_standby_usb.py` exercises the real script with Docker-command and filesystem-stat doubles only. It covers exit128/255, simultaneous stopped/missing conditions, healthy/missing expected devices under whole-bus mappings, expectations not mapped into a container, running containers with absent pins, non-running states, invalid/missing pins, non-character paths, Docker timeout/missing executable/invalid output, and sanitized logs. The full `scripts/tests` Python suite retains the existing watcher controls. Real device/container behavior and alert delivery require the owner's later validation; local tests make no deployed-availability claim.
